The app

Every later stage assumes one mental model: the container reads bean definitions, creates the objects, and connects them. Once you've wired an app by hand, you can see exactly which job Spring takes over.

BreakfastCook takes food from a Pantry, heats it on a Stove, and uses a Clock to report when it was served.

BreakfastCook
├── Pantry
├── Stove
└── Clock (from the JDK)

$ run any variant
hot baked beans, served at 11:42:33

Every variant builds these same four objects and prints the same kind of line. Only the code that creates and connects them changes.

One app, three wirings

Your main method decides, using new.

main does all the work in order. The dependencies must be created first, because the constructor call needs them. There is no container, so nothing here is a bean.

Your config class decides, and Spring calls it.

The classes in plain never mention Spring. All the Spring-specific wiring lives here, which is also why this style works for Clock, a class you can't annotate.

Spring decides, from annotations on the classes.

You no longer write a method that calls the constructor, so Spring picks one itself. scan.BreakfastCook has only one constructor, so Spring uses it and resolves its parameters by type. These classes are duplicated on purpose so you can compare them with plain.

Key terms

Inversion of control
Something other than your business code controls a job that your code would otherwise do itself. In this stage, that job is creating objects and connecting them.
Dependency injection
One way to apply IoC. A class declares what it needs, usually as constructor parameters, and whoever creates it supplies those things. plain.BreakfastCook does this without importing anything from Spring.
Container
The Spring object that creates and manages your objects. BeanFactory is its basic interface, and ApplicationContext builds on it.
Bean
An object that the container creates, configures, and manages. A Pantry you create with new in main is not a bean, even though the class is the same.
Bean definition
The container's recipe for a bean, such as its class, how to create it, and what it depends on. The container collects definitions first and creates objects later.

Inside startup

      Declaring beans

      AnnotationWhat it says
      @ComponentScanning should register this class as a bean. Here: scan.Stove.
      @ServiceA @Component that names a business role. It adds no behaviour of its own. Here: scan.BreakfastCook.
      @RepositoryA @Component for data access, and it marks the class for exception translation when that processor is registered. Here: scan.Pantry.
      @ControllerA @Component for the web layer. Spring MVC looks for it. This module doesn't use it.
      @ComponentScanSearch for those classes. With no arguments, it covers the config class's package and its subpackages.
      @ConfigurationMarks a class that declares beans.
      @BeanThe method's return value is a bean, and its parameters are the dependencies.

      Default bean names

      • Scanned class: the simple class name with a lowercase first letter. BreakfastCook becomes breakfastCook.
      • @Bean method: the method name. clock() becomes clock.

      Looking beans up

      context.getBean(BreakfastCook.class);                     // by type, as the apps do
context.getBean("breakfastCook", BreakfastCook.class);    // by name, with a checked type

      In this module, getBean appears only in main methods and tests. A main method needs a starting point, because nothing injects into it. Everywhere else, classes declare their dependencies and receive them, which keeps them testable and free of Spring lookups. The by-name form isn't used in the module, so try it yourself.

      BeanFactory vs. ApplicationContext

      BeanFactoryVsContextApp registers the same Probe class in both containers. Probe prints a line from its constructor, and isWired() reports whether its @Autowired setter was called. Look at where the constructor line appears in each half.

      BeanFactory: registering the definition
BeanFactory: asking for the bean
  -> Probe constructor called
BeanFactory: @Autowired honoured? false
      ApplicationContext: refreshing
  -> Probe constructor called
ApplicationContext: asking for the bean
ApplicationContext: @Autowired honoured? true
      • The bare factory is lazy. It creates Probe only when getBean asks for it.
      • The context is eager. It creates Probe during refresh(). A broken configuration therefore fails at startup, not later when a bean is first requested.
      • Annotations don't do anything on their own. @Autowired is only metadata, and a processor has to act on it. AnnotationConfigApplicationContext registers that processor, but a bare DefaultListableBeanFactory doesn't. The factory does have a clock available, so an unwired Probe can only mean that the annotation was ignored.

      Two separate differences

      Eager creation comes from being an ApplicationContext. Annotation support comes from the processors a particular context registers. Experiments 9 and 10 pull them apart:

      ContainerSingleton created@Autowired
      DefaultListableBeanFactoryOn first getBeanIgnored
      …plus preInstantiateSingletons()When you call itIgnored
      …plus the processor, added by handWhen you call itHonoured
      GenericApplicationContextDuring refresh()Ignored
      AnnotationConfigApplicationContextDuring refresh()Honoured

      Probe uses setter injection because, by default, a bare factory can't supply constructor arguments. With constructor injection, the demo would fail before it could report anything.

      Why the code looks like this

      • The context is opened with try-with-resources. Closing it shuts down the container and destroys its singletons. Stage 4 covers what your beans can do at that moment.
      • The clock is injected. A class that called LocalTime.now() directly would print a different time on every run. Injecting a Clock lets a test supply a fixed time and check the exact output.
      • @Autowired is absent from scan.BreakfastCook. A class with a single constructor uses it for injection, so there is nothing to choose between.
